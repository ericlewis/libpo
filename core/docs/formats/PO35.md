# PO-35 / PO-137

[Format overview](../PO_FORMATS.md) · [Documentation](../README.md)

The retained PO-35/137 corpus uses one shared backup grammar and record layout.
The [PO-35 guide](https://teenage.engineering/guides/po-35/en) and
[PO-137 guide](https://teenage.engineering/guides/po-137/en) list the same eight
voices, effect controls and four adjustable speech parameters. This is not
proof of identical table contents, firmware or rendered audio. The two public
reference banks have different drum patches, patterns and speech, as well as
differences in four of eight `7BE7` tables and two of eight `1C7F` tables.
Offline transfer roundtrips preserve both references; physical cross-loading
and exact synthesis parity remain unverified.

### Record tags and indexed tables

Tags: `37B2` drum patches; `7BE7` and `1C7F` indexed tables; `CCB2` pattern,
`29FF` empty pattern; `DC32` speech header, `73B0` records, `29A1` section end;
`84D8` settings. The indexed tables' semantics remain unresolved.

Both indexed-table layouts are fixed in the inspected corpus:

| Tag | Payload bytes | Layout |
| --- | ---: | --- |
| `7BE7` | 9 | One index byte followed by eight uninterpreted bytes |
| `1C7F` | 13 | One index byte followed by twelve uninterpreted bytes |

All 800 records of each tag across 100 retained capture identities match these
sizes. The table codecs preserve the full index byte and every body byte rather
than restrict values to observed indices 0..7. The nonzero bytes of `1C7F` can
resemble three little-endian integers, but that does not establish integer
fields instead of bytes with padding. Desktop Bitspeek enums and candidate
gain/detune interpretations are not imposed on either table.

There is no voice-independent scalar conversion for byte 2 between the two
retained `7BE7` table variants: source value 18 becomes 21 at index 2 but 14 at
index 6, with every other byte within each paired record unchanged. This rules
out a conversion using that byte alone, not a gain role or an index-dependent
interpretation. Preserve the records rather than normalize one variant into
the other.

### Drum patches and settings

The 43-byte drum payload is identical to PO-32: selector followed by 21 LE16
parameters normalized by 65535. Left/right selectors are `0x10 | (slot-1)` and
`0x20 | (slot-1)`. There are sixteen pairs of patches, not sixteen simultaneous
hardware voices. Reuse the existing PO-32 patch codec and synth.

Settings payload: 156 bytes plus active pattern-chain entries.

| Offset | Bytes | Meaning |
| ---: | ---: | --- |
| 0 | 120 | Fifteen 8-byte speech-control records; first two bytes are raw pitch/formant controls, next two parameter bytes and four state bytes remain raw |
| 120 | 32 | Sixteen interleaved drum pitch/morph pairs |
| 152 | 1 | Tempo |
| 153 | 2 | Raw retained state; byte 153 is a swing candidate, byte 154 a candidate selected/remembered sound ID |
| 155 | 1 | Pattern-chain entry count |
| 156 | Count | Zero-based pattern indices, repeats preserved |

In the [drum-key hardware comparison](PO35_DRUM_EVENTS.md#hardware-follow-up-drum-key-and-multiplier),
byte 154 changed from 15 to 23 when the user changed drum key 1 to key 9.
This supports a combined speech/drum selected-or-remembered identifier for
those points, rather than treating the field as only a 0..15 sound-bank index.
The complete mapping and state-update semantics remain raw.

The single-packet typed codec supports at most 99 chain entries because the
packet payload limit is 255 bytes. The [PO-35 guide](https://teenage.engineering/guides/po-35/en)
describes chains of up to 64 patterns. The codec's 99-entry capacity is a
record-size limit, not evidence that a device accepts chains of 65–99 entries.

A new PO-35 readback stores the requested 240 BPM directly at byte 152.
Byte 153 varied 0 → 18 → 0 alongside reported swing changes with range 0..18,
but those captures also changed other controls. Keep byte 153 raw until an
isolated swing edit or timing measurement establishes its interpretation.

In a [synthetic control-range roundtrip](PO35_ROUNDTRIP.md), exactly six global
parameter zeros returned as ones, while every other settings byte and all 64
chain entries were preserved. All 1,536 per-step parameter bytes survived,
covering 0..255 once per control plane. This is storage evidence with a qualified
button-interaction history, not a receive-only clamping rule or a playback
calibration. Raw codecs continue preserving the original values.

### Pattern records

The [drum-event investigation](PO35_DRUM_EVENTS.md) expands the PO-32 comparison
with an isolated drum-pattern pair, a full nibble census, and an exact observed
relationship for the stored final mask. It keeps physical drum numbering and
multiplier meanings separate from those byte-level findings.
Its subsequent PO-35 hardware follow-up observes high nibbles 0/8 for drum
keys 1/9, low code 2 for displayed multiplier 2, and an additional retained
selector cochange at a zero-low-code step. It does not calibrate every value.
The [multiplier-state follow-up](PO35_MULTIPLIER_STATE.md) maps displayed 3 to
low code 3 and shows a clean 1 → 2 edit without that cochange. Do not derive an
extra step marker from the multiplier value.

Pattern payload: 183 bytes.

| Offset | Bytes | Meaning |
| ---: | ---: | --- |
| 0 | 1 | Pattern index |
| 1 | 16 | Speech slot in the high nibble, event code in the low nibble |
| 17 | 16 | Note code in the high nibble, gate-duration code in the low nibble |
| 33 | 64 | Four speech parameter bytes per step: pitch, formant, start candidate and speed candidate in that order; numeric laws remain raw |
| 97 | 16 | Drum events |
| 113 | 32 | Interleaved per-step drum pitch/morph |
| 145 | 16 | Index pairs: tested high FX/clear selection and low voice selection; full value mappings remain raw |
| 161 | 16 | Raw step state |
| 177 | 1 | Pattern key and scale in the tested PO-35 captures; exact key encoding remains raw |
| 178 | 3 | Other raw footer state |
| 181 | 2 | Stored derived mask, little-endian; preserved, not recalculated |

The factory Pattern-15 bytes `37 37 35 35` repeat four times. On the tested
PO-35, holding FX showed FX 12 steadily and voices 8/6 alternating, matching
high nibble `3` and low nibbles `7/5`. Separate pattern-only imports made the
voice-6 or voice-8 indicator steady; a matched flat-pitch speech-only
comparison of low values `0/4` produced a small audible difference consistent
with voices 1/5. Factory Pattern 4 uses `70`, `20` and `75` at selected steps;
the user observed voice 1/6 and FX 11/16 choices there. These observations
support the [lossless C byte view](../api/PO35.md#pattern-voice-and-fx-selection)
without making raw index values into a complete effect or voice DSP enum.

High value `7` displayed the FX-16 clear selection in a generated Pattern-15
test. FX 16 is a clear action, not another audible effect. The prepared files
also removed the factory long build-up, but no isolated physical clear-write
readback establishes every update rule. Low voice and high FX selections are
distinct from the speech sound slot: Pattern 15 uses speech Sound 4 and drum
Sound 16 while its voice choices alternate.

The first per-step speech parameter at offset `33 + 4*step` has an observed
pitch role. In the tested Pattern 15 it varied `128 -> 255 -> 128` and the
user heard a sweep; holding it at `128` produced flat pitch across all eight
voices. The numeric pitch scale remains unmeasured.

The second byte at `34 + 4*step` has separate PO-35 formant evidence. Later
matched Pattern-15 transfers kept every parameter constant across steps and
changed only the third byte to `24` or fourth to `160`; the user said those
appeared to change start and speed as intended, reporting displays of `12`
and roughly `-88`. Separate short transfers varied one control only on steps
5..11 and returned it to baseline, and the user reported that these worked.
These are qualitative, one-context observations. They support the storage
order and the [raw C view](../api/PO35.md#pattern-speech-controls), not a
display-to-byte or audio-rate conversion. Per-sound tune/mix metadata in the
speech header and global settings remain separate from these step locks.

The [speech-event playback tests](PO35_SPEECH_EVENTS.md) establish code `1`
as a source restart and `F` as continuation of an ongoing voice in the tested
PO-35 context. Continuation preserves position across a pattern boundary and
can apply a note change. The tested shortened gate ends the voice; later `F`
events do not restart it. Note/gate roles are observed, while their exact
key/scale and timing conversions remain separate questions. The
[typed event view](../api/PO35.md#speech-events) exposes the stored nibbles
without changing the raw pattern layout or normalizing unknown codes.

#### Pattern key and scale

The [PO-35 guide](https://teenage.engineering/guides/po-35/en) documents
pattern key and scale controls; the [device developer](https://soniccharge.com/forum/topic/1060-po-35-secret-powers)
says those values are saved per pattern. In a controlled selective SEND, three
otherwise identical speech-only patterns had user-reported keys −C, C and +C
on Major scale. Their only differing non-index byte was footer offset 177:
`A0`, `00` and `60` respectively. A second SEND retained those keys and
changed the scales to Major, Blues and Arab. Across the two decoded frames,
only byte 177 changed: `00 -> 02` for Blues and `60 -> 63` for Arab. All other
pattern, speech, patch, table and settings payload bytes matched. An
independent packet verifier checked both complete frames (94 data packets
plus a terminal packet each) and their running checksums. This physically
localizes the tested key and scale edits to byte 177; the labels come from the
user's device setup.

A later three-pattern Major-scale transfer held the same note on step 1 and
stored byte 177 as `00`, `08` and `60` for user-reported C, C-sharp and upper
+C. All other non-index pattern bytes matched. The C-to-C-sharp difference is
`0x08`, consistent with one semitone per high-five-bit increment in observed
device-authored states. The bit-2-clear bytes for reported lower -C, C,
C-sharp and upper +C read as -12, 0, +1 and +12 semitones respectively.
These points do not establish every intermediate key position.

The observed low-two-bit scale codes are `0` Major, `2` Blues and `3` Arab.
The user confirms Minor as the fourth UI option, assigning remaining code
`1`. A C-authored one-packet pattern transfer used the typed scale setter to
change only byte 177 `00 -> 01`. The PO-35 showed End; its complete selective
readback differed from the pre-edit logical payloads at exactly that byte.
The other two included patterns, settings, speech, drum patches and indexed
tables matched. This verifies stored scale editing and preservation in one
PO-35 bank, not audible Minor playback or PO-137 behavior.

The 62 distinct retained PO-35/137 pattern bodies and the device-authored
key/scale comparisons all had bit `0x04` clear. A separate C-authored
one-pattern transfer set only this bit in a known C Major pattern (`00 -> 04`).
The PO-35 showed End and read back `04` byte-exactly. After a `00` restore,
the two selective readbacks had identical settings, speech, drum patches,
indexed tables and pattern payloads except for byte 177. Other patterns were
omitted from these readbacks, so their stored state was not tested there.

Matched playback recordings retained one note every four seconds. The
thresholded audible burst was about 0.18–0.19 seconds at `04`, versus
0.30–0.33 seconds at `00`, with similar peaks and upward-shifted low-band
spectral energy. The source was quiet, short and noise-like; no reliable
fundamental-frequency ratio was measured. Bit 2 therefore affects playback
in this PO-35 pattern, but its exact role is unresolved. A simple 50-cent
playback-rate increment would not explain the much larger envelope change.

A signed five-bit key in bits 3..7 with semitone units and a signed six-bit key
in bits 2..7 with half-semitone units both fit the bit-2-clear −C/C/+C bytes.
The bit-2 playback result does not assign a numeric key unit or identify an
octave, gate or other control. The bounded
[key-step helper](../api/PO35.md#pattern-key-and-scale) exposes the observed
bit-2-clear code range −12..+12 while preserving the other bits; intermediate
steps are inferred from the packing and not individually device-validated.
Keep the raw byte for lossless storage and bit-2-set states. The user
describes the pattern-key selector as chromatic across two octaves. That spans
24 semitone intervals; both C endpoints would give 25 positions. The exact
position count was not established by these captures.
Per-step note codes and speech pitch locks are separate stored fields. The
developer notes say PATTERN-plus-knob changes take effect on release and
update every pattern in the active chain.

In 42 distinct validated frames with fewer than sixteen pattern records, the
set of transmitted pattern indices equals the active chain's index set. This
includes 19 frames with one-byte empty-pattern markers. The set of included
speech-header slots also equals the set of high nibbles in active speech events
of the included full patterns (`(event & 15) != 0`): 29 frames have no speech
groups and 13 have one complete group. This matches the selective export
described by [the PO-35 developer](https://soniccharge.com/forum/topic/1060-po-35-secret-powers),
but the recording labels do not prove which button combination produced each
frame. It is not a general rule for full banks: 46 of 47 distinct frames with
all sixteen pattern records have a one-entry chain yet transmit every pattern
slot and all fifteen speech groups. Here pattern records include both full
`CCB2` payloads and one-byte `29FF` empty markers; only three of those 47 frames
contain sixteen full patterns. Missing records must be preserved as an observed
transfer shape, without assuming a receiver clear or merge behavior.

The old mask relation was rechecked through the current native parser: all
85 full `CCB2` occurrences across 100 capture identities, including repeated
frames, match the union of `1 << (event >> 4)`
for speech event bytes with a nonzero low nibble, plus bit 15 only when an
active drum event has high nibble zero. Setting bit 15 for every active drum
matches only 59 of those 85 occurrences. Deduplicating frames leaves 82 full
occurrences; deduplicating the payloads leaves 62 patterns. The corresponding
naive-rule counts are 56/82 and 36/62. One drum-only pattern has events `0x61`
at zero-based steps 0, 4 and 8 but mask zero; zero mask therefore does not
identify an empty pattern. This is an observed relation, not a recomputation rule imposed on new
data. A truncated wider drum bitset would explain its arithmetic but is not
evidence of device implementation or a confirmed bug.

For all 150 positions whose index-pair high nibble differs from 7 across the
distinct patterns, the corresponding step-state byte indexes a position with
the same high nibble. In 38 cases it is not the current linear run's start.
Identical high-nibble sequences also occur with different step-state arrays.
This supports an effect-associated reference/history candidate, not a value
derivable solely from present runs or a verified playback pointer. Preserve
the bytes, including those retained at other positions.

Across archived continuation events, note codes, candidate voice/effect fields
and parameter values can change; one captured transition also changes slot.
The slot-changing case's playback behavior remains unverified. Continuations
must not be expanded as copies of the previous event. Inactive rows can retain
secondary state. The mask is not a simple active-step or accent bitmap;
preserve it without imposing a guessed formula on new data.

### Speech records and reconstruction

Speech header: slot byte, BE16 record count, frame-rate byte, five raw metadata
bytes. Each following record is 44 bytes: signed LE16 pitch, gain byte,
unvoiced byte, ten signed low-bank LAR values, thirty signed high-bank values.
In the reconstruction model, pitch is signed Q11 octaves relative to C4.
The low and high filter banks use 10 and 30 coefficients at 8 and 24 kHz.
Gain, noise, voice characters and effects are not fully mapped. See the
[speech analysis API](../api/PO35.md#po-35-speech-analysis) and
[speech renderer](../api/PO35.md#po-35-speech-rendering) for model limits.

Gain and unvoiced values remain unsigned raw codes. The unvoiced byte spans
254 distinct values in the inspected speech bodies, so it is not a boolean.
Bitspeek analysis informs the reconstruction model but does not establish
device gain/noise laws, header metadata units or equivalent voice selectors.
Zero excitation gain also does not guarantee immediate zero PCM when a
renderer retains filter history; no silence predicate or forced terminator is
inferred from the record values.

### Root Tuning and Normal Tone Controls

The speech header's payload bytes 6..7 (`metadata[2..3]`) store the root-control
value as a signed big-endian 16-bit integer. PO-35 readbacks matched displayed
+2047 to `07 FF` and -2036 to `F8 0C`. A positive-endpoint edit changed only
those two selected-header bytes while retaining the complete 17,204-byte
speech body. The negative-endpoint take also changed header byte 4; its
additional change remains unassigned. Both endpoint readings agree with the
root representation, but do not establish octave units, sign of audible pitch
change or exact knob limits. In particular, Q11 octaves remains a hypothesis.

Normal pitch and formant live separately in the first two bytes of each
eight-byte per-sound settings record. For Sound 1, independent PO-35 knob A
and B interactions changed only their respective settings bytes 0 and 1.
Each stored `01` at displayed -127 and `FF` at displayed +127; every unrelated
settings byte was retained. These endpoints fit a 128-centered display
encoding without establishing its interior or acoustic law. Remaining
parameter/state bytes and per-step numeric behavior stay raw.

The [typed control views](../api/PO35.md#speech-control-views) expose the tone
bytes and signed root value without changing existing struct layouts or
normalizing unknown values. These physical control checks used a PO-35;
PO-137 coverage remains the inspected shared grammar, not a matching hardware
experiment. Header bytes 4, 5 and 8 retain candidate roles and raw storage.

In decoded logical payloads, a matched retained pair differs only at settings
byte 152: global tempo changes from 140 to 120. All 15 speech headers and 484
speech-data payloads remain identical.
Speech-header byte 4 retains values 120 or 123 by slot, so it is neither a copy
of current global tempo nor a function of that tempo alone. Recording-time or
sample-associated tempo remains a candidate; no header units are established.
The [device developer](https://soniccharge.com/forum/topic/1060-po-35-secret-powers)
describes a separate sample-BPM knob in tune mode, making a per-sample value
plausible. The retained captures contain no isolated edit of that knob, so
byte 4 cannot yet be named as its stored value.

Three retained speech groups share the same nine-byte header yet contain two
different 640-record bodies. Header metadata therefore does not uniquely
identify the current speech body. No identical body with different header
metadata was found in that earlier corpus. The subsequent root-control
readbacks above supply such edits; the remaining metadata stays raw.

All 56 distinct speech bodies in the inspected corpus end with zero gain and
the previous record's other 43 bytes. Interior silent records have exceptions.
This is evidence of held analysis state during silence and a recurring ending,
not a mandatory sentinel or proof of an append-versus-overwrite rule. The PCM
encoder does not claim to reproduce exact device release behavior.

The raw header can represent up to 65,535 records. The hosted speech editor
uses a separate 640-record creation policy: 8 seconds at 80 fps, 10⅔ seconds
at 60 fps, 16 seconds at 40 fps or 32 seconds at 20 fps. Magnus Lidström
[documents the four rates, the 80 fps default and longer recording at lower rates](https://soniccharge.com/forum/topic/1060-po-35-secret-powers).
The durations above follow from `640 / fps`; the exact lower-rate limits are
an inference used by the editor, not verified hardware acceptance limits.
Parsers retain larger valid raw groups without imposing this creation policy.

Speech replacement preserves the slot and opaque header bytes 4–8, updates
only the BE16 record count and frame-rate byte, and replaces the group's
record packets. It retains settings, drum patches, patterns and other groups.
Unknown extensions inside a selected group make replacement ambiguous and
are rejected by the hosted editor.
